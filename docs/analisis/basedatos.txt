✅ Fase 1: Núcleo de resolución de tenant.
Objetivo
Definir el componente central que identifique el tenant a partir de cada solicitud y determine de forma consistente qué base de datos debe usarse.

Descripción
Esta fase establece el corazón del modelo multi-tenant. La resolución de tenant no debe quedar distribuida en controladores o módulos, sino concentrada en un componente único, equivalente al papel que cumple el núcleo HTTP en Odoo. Este componente debe inspeccionar la solicitud entrante, normalizar el host, identificar el tenant, determinar si la ruta requiere o no base de datos y resolver la conexión correcta antes de que la lógica funcional se ejecute.

Alcance
Extraer la lógica de resolución de tenant a un componente claro tipo TenantResolver.
Separar tres pasos: normalizar host, resolver tenant y resolver URL de BD.
Agregar estrategia dual: convención (cliente1.midominio.com -> cliente1) y tabla central de mapeo.
Definir comportamiento equivalente a auth='none': rutas sin tenant, rutas tenant-aware y rutas admin globales.
Definir el contrato de salida del resolvedor: tenant_id, tenant_key, host, db_key, db_url y modo de acceso.

Entregables
Especificación del componente TenantResolver.
Definición de reglas de resolución por host.
Clasificación formal de rutas nodb, tenant-aware y admin global.
Contrato técnico del contexto mínimo por request.

Criterio de aceptación
Cualquier request puede clasificarse en sin BD, BD por host o BD administrativa.
La resolución del tenant ocurre en un solo punto del sistema.
La salida del resolvedor es estable y reutilizable por middleware, auth y capa de datos.

✅ Fase 2: Capa de conexión multi-BD.
Objetivo
Diseñar la capa responsable de administrar conexiones, sesiones y pools por tenant, garantizando aislamiento entre bases de datos y controlando el ciclo de vida de los recursos.

Descripción
Una vez definido cómo se resuelve el tenant, el siguiente paso es formalizar la capa que entrega la conexión correcta a la base de datos correspondiente. Esta capa debe concentrar toda la lógica de creación, reutilización, descarte y monitoreo de engines y sesiones. No debe existir acceso directo a conexiones globales fuera de este punto. El objetivo es que cada request use únicamente la base de datos del tenant resuelto, sin contaminar el contexto de otros tenants y sin degradar el rendimiento por creación excesiva de conexiones.

Alcance
Formalizar un componente DatabaseRouter sobre lo que hoy realiza fastapi_modulo/db.py.
Controlar el ciclo de vida de engine, sessionmaker, pool y dispose.
Definir política de reutilización de engines por tenant.
Definir límites: máximo de pools activos, TTL de engines inactivos y estrategia de reconexión.
Separar manejo de SQLite de desarrollo y PostgreSQL de producción bajo una interfaz común.
Incluir protección ante rutas inválidas, directorios no accesibles y bases no disponibles.
Agregar observabilidad mínima: logs con tenant, host, db_url redacted y tiempo de resolución.

Responsabilidades del DatabaseRouter
Recibir el contexto resuelto por TenantResolver.
Traducir db_key o db_url en engine utilizable.
Crear sessionmaker por tenant.
Reusar engines existentes cuando corresponda.
Liberar engines inactivos o inválidos.
Reportar errores de conexión de forma consistente.

Entregables
Especificación del DatabaseRouter.
Política de manejo de pools y sesiones.
Contrato único para obtener sesión por tenant.
Definición de estrategia de fallback y manejo de errores de conexión.
Lineamientos de observabilidad para conexiones multi-BD.

Criterio de aceptación
Dos tenants concurrentes usan sesiones separadas sin fuga de contexto.
No existe dependencia funcional de una sesión global única.
La capa de conexión puede operar con múltiples bases de datos sin duplicar lógica en módulos.
Los errores de acceso a base de datos quedan centralizados y diagnosticables.

✅ Fase 7: Autenticación y seguridad.
Objetivo
Definir un modelo de autenticación y seguridad compatible con la arquitectura multi-tenant, garantizando que cada tenant mantenga aislamiento de acceso, sesiones, permisos y contexto operativo.

Descripción
La arquitectura multi-tenant requiere que la autenticación deje de depender de supuestos globales y opere siempre dentro del contexto del tenant resuelto. Esta fase establece cómo se validarán usuarios, cómo se mantendrán las sesiones, cómo se separarán las rutas administrativas globales de las rutas del tenant y qué controles impedirán accesos cruzados o manipulación del contexto por dominio.

La seguridad debe considerar no solo la validación del usuario, sino también la integridad del tenant activo, el estado operativo del dominio y la correspondencia estricta entre sesión, host y base de datos. El objetivo es que el sistema nunca permita que una credencial o cookie emitida para un tenant pueda reutilizarse en otro.

Alcance

Alinear cookies, tokens y sesiones con el dominio y el tenant resuelto.
Agregar validaciones para impedir host spoofing, acceso cruzado y uso de un tenant inactivo.
Definir rutas administrativas globales con autenticación separada del tenant app.
Definir políticas de expiración, revocación y renovación de sesiones por tenant.
Separar permisos estructurales del sistema de permisos funcionales por app instalada.
Preparar soporte para auditoría de autenticación y eventos sensibles por tenant.

Controles mínimos requeridos
validación estricta de host contra tenant registrado
asociación obligatoria entre sesión y tenant
rechazo de sesiones emitidas para otro dominio
bloqueo de tenants suspendidos o en error
aislamiento de cookies por dominio y alcance
auditoría de logins, logout, intentos fallidos y accesos administrativos

Entregables
Definición del modelo de autenticación multi-tenant.
Política de sesiones y cookies por tenant.
Reglas de seguridad para rutas tenant-aware y rutas admin globales.
Controles de validación de dominio y estado del tenant.
Base para auditoría de seguridad por tenant.

Criterio de aceptación
Una sesión emitida para clienteA no sirve en clienteB.
El sistema bloquea acceso cuando el host no coincide con el tenant de la sesión.
Las rutas administrativas globales están separadas del acceso funcional de cada tenant.
Los eventos de autenticación y seguridad quedan registrados con contexto de tenant.

✅ Fase 8: Migraciones y operación.
Objetivo
Definir el modelo operativo para evolucionar, mantener y recuperar el sistema multi-tenant, asegurando que cada tenant pueda migrarse, respaldarse y restaurarse de forma controlada.

Descripción
La arquitectura multi-tenant no queda completa solo con la provisión inicial. El sistema debe contar con un mecanismo formal para aplicar cambios de esquema, actualizar módulos, sembrar datos controlados y operar múltiples tenants sin perder trazabilidad ni capacidad de recuperación. Esta fase establece cómo se ejecutarán las migraciones por tenant, cómo se manejará la base administrativa central y qué procedimientos operativos mínimos deben existir para soporte, respaldo y restauración.

La operación debe contemplar que distintos tenants pueden estar en diferentes estados, que una migración puede fallar parcialmente y que la plataforma debe contar con herramientas para identificar, corregir y recuperar esos casos sin afectar a los demás tenants.

Alcance
Crear runner de migraciones por tenant y por BD administrativa.
Definir orden formal de ejecución: migración core, migración de módulos y seed opcional.
Definir política de versionado de esquema por tenant.
Agregar backups por tenant, restore aislado y smoke tests post-migración.
Definir procedimiento de rollback operativo cuando una actualización falle.
Registrar historial de migraciones ejecutadas y estado final por tenant.
Preparar ejecución selectiva: migrar un tenant, un grupo de tenants o toda la plataforma.

Capacidades mínimas requeridas
migración individual por tenant
migración global coordinada
registro de versión de esquema por tenant
backups independientes por base de datos
restore aislado sin afectar otros tenants
smoke tests posteriores a migración
bitácora de errores y estado de recuperación

Entregables
Diseño del runner de migraciones multi-tenant.
Política de versionado y orden de actualización.
Procedimiento de backup y restore por tenant.
Definición de rollback operativo.
Base de trazabilidad para historial de migraciones y estado por tenant.

Criterio de aceptación
El sistema puede actualizar N tenants con trazabilidad y control de errores.
Una falla de migración en un tenant no compromete a los demás.
Existe respaldo y restauración aislada por tenant.
Cada tenant conserva registro claro de versión, migraciones aplicadas y estado operativo.

✅ Fase 9: Observabilidad y soporte.
Objetivo
Dotar a la plataforma multi-tenant de mecanismos de monitoreo, diagnóstico y soporte operativo que permitan identificar el estado de cada tenant, detectar errores con contexto suficiente y resolver incidentes sin depender de inspección manual del código.

Descripción
En una plataforma donde múltiples dominios operan sobre distintas bases de datos, la visibilidad operativa es obligatoria. Esta fase define la información que debe registrarse, medirse y exponerse para que soporte y operación puedan entender qué tenant resolvió una solicitud, qué base de datos utilizó, qué versión de esquema tiene, qué módulos están activos y qué errores o degradaciones se están presentando.

La observabilidad no debe limitarse a logs. También debe incluir métricas, trazabilidad de migraciones, paneles administrativos, vistas de estado por tenant y herramientas de diagnóstico rápido que permitan aislar incidentes y validar la salud operativa de la plataforma.

Alcance
Añadir logs estructurados con tenant, host, tipo de acceso, errores por tenant y latencia por resolución.
Registrar métricas de conexiones activas, tiempos de respuesta, fallos de autenticación, errores de migración y estado de provisión.
Crear panel o endpoints administrativos para listar tenants, estado, versión de esquema, apps instaladas y última migración.
Agregar diagnóstico rápido: qué tenant resolvió esta request, a qué BD fue y bajo qué contexto se ejecutó.
Definir alertas mínimas para fallas críticas de tenant, base de datos, autenticación y provisión.
Preparar base de soporte para auditoría operativa y análisis posterior de incidentes.

Capacidades mínimas requeridas
logs estructurados por tenant
métricas operativas por dominio y por base de datos
consulta del estado actual de cada tenant
diagnóstico de resolución host -> tenant -> base de datos
historial de migraciones y provisión
alertas básicas ante errores críticos repetitivos

Entregables
Especificación de observabilidad multi-tenant.
Esquema de logs y métricas por tenant.
Panel o endpoints administrativos de estado.
Herramientas de diagnóstico rápido para soporte.
Base de eventos operativos y de auditoría técnica.

Criterio de aceptación
Soporte puede diagnosticar un tenant sin inspección manual del código.
La plataforma puede informar qué tenant atendió una solicitud y qué base de datos utilizó.
Los errores quedan trazados con suficiente contexto para análisis y recuperación.
Existe visibilidad operativa de tenants, migraciones, provisión y estado general del sistema.

✅ Fase Adicional: Consolidación del Núcleo del Sistema

Objetivo
Consolidar los módulos web y modulo_base como núcleo técnico de SIPET, de modo que el sistema pueda evolucionar hacia una arquitectura multi-tenant donde cada dominio opere con su propia base de datos y con un conjunto independiente de aplicaciones instaladas.

Descripción
Antes de habilitar la instalación de apps por tenant, es necesario estabilizar la base estructural del sistema. El módulo web debe quedar como la capa única de entrada HTTP, responsable de recibir solicitudes, identificar el dominio, resolver el tenant, seleccionar la base de datos correspondiente, aplicar middlewares, autenticar usuarios y despachar la ejecución hacia los módulos funcionales. El módulo modulo_base debe convertirse en la capa común sobre la que se construirán todas las apps instalables, reuniendo servicios transversales y contratos técnicos compartidos.

Esta fase busca eliminar la dispersión de lógica estructural, evitar duplicidades entre módulos y establecer una separación clara entre el núcleo del sistema y las aplicaciones de negocio. A partir de esta consolidación, cualquier módulo funcional deberá integrarse siguiendo un estándar único de registro, instalación, dependencias, rutas, permisos, assets y tareas.

Alcance

Consolidar en web toda la lógica de entrada, contexto de request, autenticación, middleware, tenant resolution y dispatch.
Consolidar en modulo_base los servicios reutilizables del sistema.
Eliminar duplicidades entre módulos base y módulos funcionales.
Definir el contrato técnico obligatorio para módulos instalables.
Separar formalmente el core de la plataforma y las apps de negocio.
Componentes a consolidar en web

resolución de dominio y tenant
selección dinámica de base de datos
middlewares comunes
autenticación y sesión
backend shell y layout base
despacho de rutas y registro central de módulos
Componentes a consolidar en modulo_base

respuestas estándar
seguridad reutilizable
auditoría base
utilidades de repositorio
servicios compartidos
cache y locking
tareas base
layouts, plantillas y componentes comunes
contratos de bootstrap e instalación de módulos
Entregables

definición clara de responsabilidades entre web y modulo_base
refactor del código transversal hoy disperso
interfaz estándar para módulos instalables
inventario de dependencias compartidas y duplicidades eliminadas
documentación técnica del núcleo consolidado
Criterios de aceptación

web funciona como punto único de entrada y resolución de contexto
modulo_base concentra las capacidades transversales del sistema
los módulos funcionales ya no implementan servicios estructurales repetidos
existe un contrato uniforme para registrar e instalar módulos
la arquitectura queda preparada para activar apps distintas por tenant sin mezclar lógica global
Justificación
Esta fase es obligatoria porque la arquitectura multi-tenant no será estable si el sistema mantiene lógica compartida dispersa, dependencias cruzadas o comportamiento global dentro de módulos funcionales. La consolidación del núcleo es la condición previa para permitir que cada dominio instale únicamente las apps que necesite, con aislamiento técnico, operativo y funcional.

Orden recomendado

Resolver arquitectura y contratos.
Consolidar TenantResolver + DatabaseRouter.
Meter middleware y contexto único.
Crear BD administrativa de tenants.
Implementar alta/migración de tenants.
Adaptar módulos y auth.
Cerrar operación, monitoreo y tooling.
Riesgos

Mezcla accidental de datos por uso de sesiones globales.
Módulos que escriben archivos o cachés compartidos entre tenants.
Crecimiento descontrolado de pools si cada host crea un engine sin política de descarte.
Migraciones incompletas si no existe inventario por tenant y versión.
Primer sprint sugerido

Middleware tenant-aware.
Tabla central tenants.
CLI create-tenant y migrate-tenant.
